# Prompt policy

Assetgrove refuses a request whose prompts name a living artist's style, a studio, a game, a copyrighted character or a real person. A name on its list refuses before anything is spent; a phrase such as "in the style of" or a name that is also an ordinary word is decided by a model, with the words around it, when the run starts. It is best-effort.

## What is checked

Every paid command's free plan step (`plan`, `apply`, `stage`, `generate-sheet`, `import`, `materials`, `look-dev`, `animation-qa`, `fix-frame`, `identity-eval`, `identity-check`) collects the request's prompt text, each string kept with the part it came from:

- the spec's strings, minus the fields that are files or ids rather than text: `assetId` and `keyPose`;
- the brief;
- the bible's fields that feed prompts (its tone fields, and its Do's and Don'ts, which the model check is told are rules the art must follow), minus its reference paths (`anchors.*.*.path`, `identities.*.turnaround`, `identities.*.references`, and a stage bible's `references.*.path` and `perspective`);
- the prompt template's body;
- at `apply`, the saved plan's input files (spec, brief, bible, template), labelled as the plan step labels them, and the text the compiler wrote in its prompts, labelled model-written: the prompt and negative before the directives the plan appends, and only where they differ from the template's own (a plan the template wrote has no model-written text; a prompt that does not split that way counts whole as other text; digests and formats feed no prompt);
- the free-text options a prompt carries: `fix-frame`'s `--family`, `--subject` and `--note`; `animation-qa`'s `--family` and `--subject` when it makes vision calls; `import`'s `--subject` and `--hints` when it proposes a grouping;
- the target profile's text a prompt carries: the motion template `generate-sheet` states (its description and beat names) and the groom seasons and their traits `look-dev` describes.

Which strings are left out is decided by field, never by what a string looks like: the files a request hashes as inputs and the asset id (`NON_TEXT_FIELDS` in `src/policy/text.ts`). Every other string is prompt text whatever it ends in, so `refs/blizzard_overlay.png` in a text field is checked, and a key pose at `poses/npc-mario-baker.psd` is not. The same fields stay out of the prompt `plan` and `apply` send: the planned prompt carries the spec without its `assetId` and `keyPose`, so for those commands the final-prompt check below reads no path or id the plan step left out, and an asset id such as `npc-mario-baker` neither refuses at the plan step nor after the compiler call. The asset id still names the files, the manifest and the provenance. A spec with no `subject` uses its asset id as the subject, and the commands whose prompts name the subject still write it there: `stage` (the `Subject:` line of its still and strip prompts, a `character-3d` stage's prompts, and its cutout decision), `generate-sheet` and `look-dev`. In those commands the asset id is prompt text: the final-prompt check reads it, so an id holding a blocklisted name exits 9 before the image or model call. Give the spec a `subject` to keep the id out of their prompts.

The text is normalised (invisible format characters such as soft hyphens and zero-width spaces removed, NFKC, lower case, diacritics removed, every run of spaces and punctuation one space) and matched against `policy/blocklist.json` (`format: "assetgrove-blocklist/1"`, shipped with the package) on word boundaries; a two-word term also matches run together.

The free check refuses only an unambiguous name (artist, studio, game, character or person): exit 9 `prompt_refused` with `error.policy`: `match` (`term`, `kind`), `blocklistSha256`, `textSha256`, `verdict` and `allowedBy`. Nothing is called, spent or written, and it makes no provider call. The plan step, `--dry-run`, `estimate`, the `ProviderSet`'s final-prompt check and every other free check refuse the same way.

Two kinds of hit refuse nothing by themselves: a phrase ("in the style of", "inspired by", "imitate", "recreate", "game called") and a name marked `"ambiguous": true` in the blocklist (a name that is also an ordinary word or a given name). Each is recorded in the record's `hits` with its `term`, `kind`, `ambiguous`, `part` and `context` (up to 12 normalised words either side). `--dry-run` and the plan step report them as decided by the model check when the run starts.

## The model check

A blocklist misses paraphrases and cannot tell a phrase used to copy from the same phrase used innocently, so the text that passes the free check also goes to a model. When a request carries prompt text, its plan holds one `prompt-policy` job: any reading calls (next section), then one Boolean decide call on the decisions role (`roles.decisions` or `routes.prompt-policy`; by default the gateway's `perplexity/pplx-decider-v1.2`, $0.001 an answer). The forecast, `--dry-run`, `estimate` and the request digest count it. After the spend is confirmed, it is the run's first call, before any image, vision or model call. The model is given the prompt as labelled parts: spec strings; brief; bible tone fields; bible Do's and Don'ts, marked as rules the art must follow; template body; other text (notes, subjects, profile text); the compiler-written prompt and negative prompt, marked model-written; and the hits with their context. So a bible rule not to imitate the look of any named game is read as a rule, and an ambiguous name is decided by its sentence, with no global allow entry. The answer:

- the model's probability that the text asks to copy a specific artist, studio, game, copyrighted character or real person is at or above the route's `refuseAt` (0.8 on the default route): exit 9 `prompt_refused`, with `error.policy` carrying `model` and `probability`, and no other call runs;
- at or above the route's `confirmAt` (0.5 on the default route) and below `refuseAt`, the request is borderline: the record says `borderline: true`, and a person is asked, as for spend (next section). Once cleared, the run goes on and the record carries `clearedBy` (`id`, `method`);
- below `confirmAt`: the run goes on;
- the call fails or answers out of type: exit 4 `provider_error`, and no other call runs;
- no configured provider serves the decisions role: the plan step exits 2 `route_unavailable`, before anything is called.

Compiler-written text is never the reason a person's request exits 9 after spend. At `plan`, a name in the compiler's output falls back for free to the template prompt (the compiler's `fallbackReason`, and `promptPolicy.fallback`); phrase hits in it are saved and decided by apply's check. A run whose prompt text has model-written parts (`apply` of a plan the compiler wrote) forecasts two prompt-policy calls: when the first refuses, a second decides on the person-written parts alone. If it allows, the run uses the repository template's prompt and records why in `promptPolicy.fallback`; if it refuses, exit 9. An `apply` of a plan the template wrote has no model-written parts: one call, and its refusal exits 9. `plan` forecasts its own one call plus its apply's (two when the compiler can run, else one).

### The cut per route and the middle band

A decision model's probability is not calibrated across models: on the anthropic and openai adapters it is a number the model writes in structured output. So the cut is recorded per route in `policy/prompt-policy-cuts.json` (`format: "assetgrove-prompt-policy-cuts/1"`, shipped with the package): one entry per `<adapter>:<model>`, each with `confirmAt`, `refuseAt`, the real check and fixture that measure it, and, once a real run has recorded them, the measured `refusalRate` and `falseRefusalRate`, which must then meet the bars (both or neither, else the file is refused). The default route, `vercel-ai-gateway:perplexity/pplx-decider-v1.2`, is the one route the bars were met on: `confirmAt` 0.5, the cut they were met at, and `refuseAt` 0.8. Its rates are not yet recorded in the entry: they were not written down when the bars were first met, and the red-team set has gained rows since. The real check prints the entry with the rates it measured, to record. The scripted test stand-in takes the default route's entry. A developer's own measurement of another route goes in the settings' `promptPolicy.cuts` ([settings.md](settings.md#roles-and-routes)), with the two rates it met the bars at, and is used over the package's entry. When the decisions role (or `routes.prompt-policy`) names a route with neither, a request that carries prompt text exits 2 `route_unavailable` at the plan step, naming the route and the file, before anything is spent: the check does not run on a route whose rates no one measured. Measure the route with `test/real/prompt-policy.real.ts` and add its entry to use it.

A borderline answer does not end a confirmed run with exit 9. It goes to the same person confirmation as spend, a confirmation of kind `policy` whose request names the run's digest, the policy text's hash, the deciding model and its probability: at a TTY or in an MCP client's form it is asked inline; otherwise exit 8 `confirmation_required`, with `error.confirmation` and the request saved for `assetgrove confirm <id>`. Run the command again once it is confirmed: the journaled prompt-policy answer is reused, not paid again, and the record clears that request only, once. Headless settings do not clear it: a person must. Compiler-written text gets the second call (above) when the first answer is borderline or refused, as before.

### Ambiguous names: the reading call

A name marked `"ambiguous": true` in the blocklist is a protected name that is also an ordinary word or a given name: a kind of weather, a kind of star, a common first name. The list stays the free refusal for unambiguous names; only for these does the hit go to a model, and the question asked is what the word refers to in this request, not whether the request copies.

For each distinct ambiguous name that a person-written part holds, the run's prompt-policy job makes one **reading call** before its Boolean call: a Choice decide call on the same `prompt-policy` operation and route (decisions role; by default $0.001 an answer). It is given the term, its kind, each sentence it appears in (its part and up to 12 words either side) and the labelled prompt parts, and chooses one of three readings:

- `protected`: the protected name itself. The request exits 9 `prompt_refused`, `error.policy.readings` names the term, and no other call runs.
- `word`: an ordinary word.
- `other-name`: an unrelated name that happens to be the same.

Only `protected` refuses. Each answer is recorded in the request's policy record as `readings` (`term`, `kind`, `reading`, `model` as `<provider>:prompt-policy:<model>`, and `probability` when the model reported one), in the run record and provenance like the rest of the record. A name read as `word` or `other-name` is taken off the Boolean call's flagged words, and that call is told it was read as not the protected name. So "heavy" weather over a snow level, a red star of that size in a skybox, or a baker NPC who shares a character's first name goes through with no allow entry, and the answer holds for that request only. An ambiguous name found only in compiler-written text gets no reading call: it stays with the Boolean call, where compiler-written text falls back to the template's prompt as below.

The calls are counted wherever the check is: the forecast, `--dry-run`, `estimate` and the request digest count one reading call per such name on top of the Boolean call or calls. `plan` forecasts them for its own check and again for its `apply`. They are made only inside the confirmed run, journaled like every call, and reserved under the run's cap; a call that fails or answers out of type exits 4 `provider_error`.

So the check fails closed: a run never goes on without it. It is journaled like every call, so a resumed run does not pay for it twice. It is reserved under the run's cap, and what it spent counts against that same cap for the rest of the run. The run record and each candidate's provenance carry the record with the deciding answer's `model` (`<provider>:prompt-policy:<model>`) and `probability`, the `verdict`, the `hits`, any `fallback`, and `checks`: every model answer the run got, each with its `scope` (`all` parts, or the `person`'s parts alone), `model`, `probability` and `refused`, the one the outcome follows marked `decided`.

The policy is measured on `test/fixtures/prompt-policy/red-team.jsonl`: prompts by category: `name` (refused for free), `phrase` (decided by the model, the expectation per row), `paraphrase`, `lookalike` and `plain`, each with an optional `part` (rules, text, model-negative) and each `source: "team"` or `"outside"`, an outside row with its public https reference. Rows tagged with a `part` of `rules` or `tone` are shaped like the inputs that reach the check: Do's and Don'ts, negated sentences ("don't imitate the look of any named game") and front-matter word lists. [docs/decisions.md](decisions.md#prompt-policy-bars) sets the bars, a refusal rate of at least 0.9 and a false-refusal rate of at most 0.1, and the real check `test/real/prompt-policy.real.ts` fails below them. It runs on the route's cut from `policy/prompt-policy-cuts.json` (and fails on a route with none); a borderline row does not run without a person, so it counts as stopped for both rates (refused on a must-refuse row, a false refusal on an allowed one), exactly as a single cut at `confirmAt` would; it prints the borderline rate beside them.

A `ProviderSet` runs the free check on every final prompt again before an image or model call, so a name in a prompt assembled after the plan step is refused too (exit 9, no call).

The normalised text's sha256 is the WorkPlan's `policyTextSha256`, part of the request digest. The `promptPolicy` record goes in `request.json`, the run record and, for `apply`, each candidate's provenance.

## Allow terms

An ambiguous name no longer needs an allow term: the reading call decides it from its sentence, for that request only. The developer settings' `promptPolicy.allow` lists terms the policy lets through for good, for a term that is an ordinary word in a world and that the developer does not want decided each run; it clears any hit, name or phrase, and each one that cleared a hit is recorded in `allowedBy`. Allow terms are the developer's decision and live in the settings, never in a shared file.

## What it cannot do

The policy reads text only, and a phrase hit is decided by a model, not refused for free, so it can be wrong both ways, at the rates the red-team set measures. It cannot see reference images, so an anchor, key pose or turnaround copied from someone else's work passes it. It cannot police a developer's own models: a fine-tuned or local model trained on someone's style produces that style from an innocent prompt. Its list is short, and a determined user can describe a style in words neither the list nor the model recognises. The person who picks each asset stays responsible for it.

Names in `policy/` and `test/fixtures/prompt-policy/` are the one exemption from the rule that no other game is named in the repository (docs/decisions.md).
